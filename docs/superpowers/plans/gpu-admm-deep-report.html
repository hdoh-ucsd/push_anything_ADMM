The GPU ADMM Investigation

We set out to move the C3+ ADMM inner loop onto an RTX 5070 Ti. It does not work, and the reason is not implementation quality — it is that our quadratic program is small and its Hessian is 0.16% dense. One ADMM iteration is less arithmetic than it costs to launch a GPU kernel.

Four independent measurements, each on real corpus matrices at n = 639, m = 439. Every figure in this report names the script that produces it.

Foundation

Where the port's time actually goes

Before asking whether a GPU helps, we need to know what it would be helping with. A wall-clock section profile at HEAD covers 455 of the measured 472 ms/tick (96%), so this is the whole budget rather than a sample. (cProfile is useless here — it cannot see Drake's pybind11 instance methods, so Drake's solve time gets folded into the caller's self time.)

That resolves to a single sentence: the port runs ~8,000 OSQP inner iterations per control tick at 47.5 µs each, and that is 81% of all wall time. The port is an iteration-count machine. Every optimization should be scored on one question — does it reduce the number of OSQP iterations? This is already the first hint that the GPU plan was aimed wrong: it attacked per-iteration cost, the smaller of the two factors.

Measurement 1

The hot loop, end to end

One control tick of real work — 6 samples × 3 C3+ ADMM iterations, on the matrices the CPU actually solved, both legs given identical problems:

The GPU is ten times slower. The reconciliation with the per-iteration numbers is convergence: Drake reaches eps = 1e-5 in 100–200 iterations, while our batched solver ran 20,000 without converging (primal residual stuck at 2.1e-4).

Our solver implements the plain OSQP iteration. Drake runs with Ruiz equilibration (scaling=1) and adaptive ρ; ours has neither. I had scoped both out of the plan as fidelity details — things needed to match OSQP's exact path, not its answer. On a problem with cond(K) ≈ 1.2e7 that was backwards: preconditioning is the performance.

At 74.8 µs, merely dispatching the kernels costs 1.6× Drake's entire iteration. Nothing can be built below that line. Our batched solver beats it only because batching 6 samples amortizes the launches — and it still loses to the CPU.

Measurement 3

The crossover: when a GPU would be right

A verdict of “no” is only half an answer. Sweeping problem size against Hessian density maps the plane, so the decision has a trigger instead of an opinion.

Two crossings, both close by. At our size, moving the Hessian from 0.16% to 5% dense flips 0.19× → 4.47×. At our density, doubling n from 639 to 1278 flips 0.19× → 1.58×. So roughly a doubling of horizon or contact count, or any real coupling in the cost Hessian, and the GPU becomes the right tool.

Note what the GPU column does not do: at n = 2556 its cost is 159.58 / 158.14 / 159.56 / 158.91 µs across all four densities — flat. The GPU pays the same price whether the matrix is 0.16% or 100% full, because it does dense work either way. The CPU meanwhile ranges from 9.66 to 21,849 µs across the plane. That is the whole story in one row: sparsity is free on the CPU and unavailable on the GPU.

Read this map for shape, not for our margin

These synthetic instances are numerically easier than ours — the synthetic CPU leg at our cell is 9.66 µs/iteration against the 47.5 µs measured in-run (real cond(K) ≈ 1.2e7, real m = 439 vs synthetic 304). So 0.19× is not our margin; the authoritative figure for our problem is the direct measurement, 0.74×. Both agree on the sign.

The follow-up question

Could we just use a GPU OSQP instead?

A fair challenge to all of the above: perhaps the problem is my solver, and a production GPU OSQP would do better. OSQP 1.x does ship a pluggable cuda algebra backend — the productionized descendant of the cuOSQP paper. Two findings:

It is not reachable here. osqp.algebras_available() returns ['builtin']; algebra='cuda' raises “Algebra cuda not available”. The published wheel contains only ext_builtin — osqp/cuda.py is a four-line wrapper with no extension behind it, and pip install "osqp[cuda]" fetches the same CPU wheel. cuosqp has no installable distribution for this Python/CUDA at all. Reaching it means building OSQP from source with -DOSQP_ALGEBRA_BACKEND=cuda. Separately, Drake vendors its own OSQP and always uses builtin, so even an installed GPU OSQP would require bypassing Drake and feeding P/q/A/l/u ourselves.

And it would not help. This is what Measurement 2 settles implementation-agnostically. A GPU OSQP solves one problem at a time, so unlike our batched solver it cannot amortize launches across the 6 samples — it sits at or above the 74.8 µs floor by construction, against Drake's complete 47.5 µs iteration.

Methodology

Four benchmarks that pointed the wrong way

This is the part worth keeping. Each of these was a real measurement that produced a real number, and each pointed somewhere false. They are in the order they happened, because each one set up the next.

  1. Benchmarking one operation instead of the loop — said STOP Timing cholesky_solve alone gave 0.58× and read as a clean kill. But a triangular solve is sequential back-substitution, the most GPU-hostile kernel in the iteration, while everything around it is embarrassingly parallel. Measuring the composite loop gave 4.41× with a precomputed inverse. Benchmark the loop, never its least-favourable component.
  2. Benchmarking against the wrong opponent — said GO That 4.41× was measured against dense linear algebra on the CPU, not against the sparse C++ solver the port actually runs. Against Drake the per-iteration figure is 0.74×. This is the error that authorized building the whole solver. The baseline is what production runs, not the most convenient stand-in.
  3. Benchmarking at the wrong dimensions An early figure used m = 300 where the real constraint count is m = 439. The GPU leg moved from 41.8 to 64.4 µs — from a slight win to a loss. Take dimensions from the corpus, not from a plausible round number.
  4. Scoping the wrong things out as “fidelity” Ruiz equilibration and adaptive ρ were written into the plan as out-of-scope conformance detail. They turned out to be worth 133× in iteration count. On ill-conditioned problems, preconditioning is not a fidelity detail — it is the performance.

A fifth trap was avoided only by luck: my first GIL probe showed 0.86× for both Drake and numpy and looked conclusive, until I noticed numpy's BLAS was already saturating cores in the “serial” leg. Pinning OMP_NUM_THREADS=1 made the control valid and the real answer appear. A control that agrees with your hypothesis is the one to distrust most.

Outcome

What the arc produced anyway

  • A repaired parallel sample-evaluation path Three independent defects. Worker plant contexts were built standalone, leaving geometry_query unconnected so every worker LCS build threw — swallowed by a bare except, yielding NaN costs and a dispatcher that silently never repositioned. Workers also ran a different physics model (four unforwarded constructor arguments, including controller_inertia). threads=4 went from total task failure to tight_goal=PASS(final).
  • A closed question on threading Drake's Solve does not release the GIL — 0.99× on 4 threads against a 3.99× sleep control. The reference's OpenMP parallel-for cannot translate to Python threads at any count. That retires a lever the project notes had listed as the biggest remaining speedup.
  • A 60-instance solver-level corpus Real ADMM instances with CPU golden outputs and the assembled QP matrices — any future solver change can be validated against it without a simulation run. This is what made every number in this report reproducible.
  • A measured description of the hot loop Diagonal Hessian, 9% dense KKT, cond(K) ≈ 1.2e7, 100–200 OSQP iterations per solve, ~8,000 per tick. Future performance work starts from these instead of guesses.
Recommendation

Stop here, and take the iteration-count lever instead

Nothing about this hardware or this problem size rewards a batched dense GPU solver, and completing it projects to ~1.03× for the cost of a preconditioner, an adaptive-ρ scheme, an assembly refactor and a full conformance re-validation.

The profile points somewhere specific instead. 72% of every OSQP iteration runs past convergence: on the real corpus the QPs converge at ~68 iterations but check_termination=100 makes them pay ~247. Dropping the check interval to 25 takes a solve from 16.84 to 10.23 ms — 1.65× on the 81% of wall time that is QP solving, so roughly 1.4× end-to-end. Set against the finished GPU port's projected 1.03×, that is an order of magnitude more return — from a one-line change.

It needs your authorization, not my judgement

check_termination=100 is a reference value from shared_parameters/sampling_c3_qp_settings.yaml, so changing it is an off-reference change. It has been measured only — nothing was altered — and any claim would still need the full two-tier eval. One caveat on the probe: it solves each QP cold with q_ref, where the live loop warm-starts and uses q_total = q_ref − 2ρG(δ−ω). The in-run mean of 275 sits close to the probe's 246.7, so it is representative but not the identical problem.

Revisit the GPU when the crossover map says to: a horizon or contact count roughly double today's, or a cost formulation whose Hessian is genuinely coupled rather than diagonal. At n = 639 and 0.16% density, it is the wrong instrument.
