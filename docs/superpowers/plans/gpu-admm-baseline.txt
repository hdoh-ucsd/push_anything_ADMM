VERDICT: PROCEED, with design amendment A1.

  Why the isolated gate said STOP and the loop says PROCEED: a triangular
  solve is sequential back-substitution, the single most GPU-hostile kernel
  in the iteration. Everything else in the OSQP step (two batched matvecs,
  clamp, axpy) is embarrassingly parallel. Measuring the hostile op alone
  mispredicted the composite loop.

  A1 — replace cholesky_solve in the inner loop with cholesky_inverse
  (computed once per C3+ ADMM iteration, reusing the Cholesky factor) plus
  a batched GEMV. Same FLOPs, parallel instead of sequential, 4.41x over
  CPU. Legitimate because correction C2 already establishes that K changes
  only once per C3+ iteration while the RHS changes every inner iteration.

  Amortization is guaranteed: OSQP runs with check_termination=100, so the
  inner loop cannot stop before 100 iterations -- 10x the break-even.

  Use torch.cholesky_inverse(L), NOT torch.linalg.inv: 14.0 ms vs 31.0 ms.

OPEN RISK carried into Task 7: cond(K) = 5 was measured on RANDOM SPD
matrices. Real LCS instances may be worse conditioned. Task 7 must re-check
on the corpus, acceptance: explicit-inverse vs cholesky_solve relative
error < 1e-9 on every corpus instance. If any instance fails, fall back to
cholesky_solve for that (N, n_lambda) group and re-measure.

      exec_src=current_fallback  pursued=kNewSample  best_other=-
  i.e. the controller asked for an alternative sample every tick and got
  nothing usable back, so it never repositioned, never entered c3, never
  touched the object. Final line: success=NO tight_goal=FAIL loose_goal=FAIL.
  It is "2x faster" only because it does no work.

  Also observed: curr_cost inflates from ~750 (threads=1) to ~1700 under
