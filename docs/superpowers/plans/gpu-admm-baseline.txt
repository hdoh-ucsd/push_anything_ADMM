VERDICT: PROCEED, with design amendment A1.

  Why the isolated gate said STOP and the loop says PROCEED: a triangular
  solve is sequential back-substitution, the single most GPU-hostile kernel
  in the iteration. Everything else in the OSQP step (two batched matvecs,
  clamp, axpy) is embarrassingly parallel. Measuring the hostile op alone
  mispredicted the composite loop.

  A1 — replace cholesky_solve in the inner loop with cholesky_inverse
  (computed once per C3+ ADMM iteration, reusing the Cholesky factor) plus
  a batched GEMV. Same FLOPs, parallel instead of sequential, 4.41x over
  CPU. Legitimate because correction C2 already establishes that K changes
  only once per C3+ iteration while the RHS changes every inner iteration.

  Amortization is guaranteed: OSQP runs with check_termination=100, so the
  inner loop cannot stop before 100 iterations -- 10x the break-even.

  Use torch.cholesky_inverse(L), NOT torch.linalg.inv: 14.0 ms vs 31.0 ms.

OPEN RISK carried into Task 7: cond(K) = 5 was measured on RANDOM SPD
matrices. Real LCS instances may be worse conditioned. Task 7 must re-check
on the corpus, acceptance: explicit-inverse vs cholesky_solve relative
error < 1e-9 on every corpus instance. If any instance fails, fall back to
cholesky_solve for that (N, n_lambda) group and re-measure.

=== Parallel sample-eval path: FIXED, but threading cannot help (2026-08-21) ===

THREE defects, found by systematic debugging from the repro in the Task 3
section above.

D1 (fatal) -- worker plant contexts had geometry_query unconnected.
  _lazy_init_worker_kits built them with plant.CreateDefaultContext(), which
  returns a STANDALONE LeafContext. The plant lives in a Diagram beside a
  SceneGraph, and every collision query the LCS build performs reads the
  plant's geometry_query input port, which is only wired for a subcontext
  extracted from a DIAGRAM context. So every worker raised
      InputPort::Eval(): required InputPort[0] (geometry_query) of
      System ::_::plant (MultibodyPlant<double>) is not connected
  and evaluate_sample's bare `except Exception: pass` swallowed it. Every
  worker sample came back J_n=None with a NaN cost; the dispatcher read
  best_other=nan every tick and silently degraded to never repositioning.
  Verified: 0 swallowed exceptions on a healthy serial run vs 164 on a
  broken parallel one. Fix: make_worker_plant_context() derives contexts
  from the diagram. Note a subcontext CANNOT be cloned -- Drake rejects
  Context::Clone() on a non-root context -- so the root must be created and
  the subcontext re-extracted.

D2 (silent wrong answers) -- worker LCSFormulators were built with the wrong
  physics model. The clone forwards only 7 of 11 constructor args; missing
  were controller_object_mass, controller_inertia, tshape_mesh_witnesses and
  mesh_ground_witnesses_body. All four are load-bearing (controller_inertia
  is one of the three legs of the 2026-08-15 hover root cause). Symptom
  after D1 was fixed: identical samples and identical J_n hashes, but ~2.3x
  different sample costs (best_other 896.14 vs serial 386.56 at tick 1).
  Fixed by syncing the PROCESSED attributes -- mesh_ground_witnesses_body is
  stored as .reshape(3,3).T, so re-passing it to the constructor would
  transpose twice.

D3 (latent) -- _final_aug_contact_scaling (the C3+ final-solve contact boost,
  1000 on the box lineage) and state_position_bounds were not in
  _solver_attrs_to_sync, though the controller's own comment claimed workers
  "inherit via _solver_attrs_to_sync".

  Guard added: _assert_worker_clone_covers_ctor_args() now runs once per pool
  build and RAISES if any constructor-derived state differs between parent
  and clone (context_ad exempted -- per-worker by design). This defect class
  cannot silently recur.

OUTCOME -- correctness restored, 60 s box gate, seed 0:
  threads=1            modes free=517 c3=284  goal 0.150->0.011  PASS(final)
  threads=4 BEFORE fix modes free=801 c3=0    goal 0.150->0.150  FAIL, success=NO
  threads=4 AFTER fix  modes free=679 c3=122  goal 0.150->0.019  PASS(final), success=YES

BUT THREADING STILL CANNOT SPEED THIS UP -- Drake's solve holds the GIL.
  threads=1 : 6m45s, avg_per_step_ms=472.0
  threads=4 : 6m28s, avg_per_step_ms=457.2   (~3%, and user ~= real)

  scripts/gpu/gil_probe.py, BLAS pinned to 1 thread so the controls are valid:
    control sleep     3.99x   (GIL released -- control valid)
    control blas      3.67x   (GIL released -- control valid)
    drake OsqpSolver  0.99x   (GIL NOT released)

  The reference's `#pragma omp parallel for` over samples does not translate
  to Python threads: pybind11 holds the GIL through Solve(), so the pool
  serializes. num_outer_threads is therefore NOT a usable speedup lever in
  the Python port at all, no matter how many threads. Real options are
  multiprocessing (Drake objects are not trivially picklable) or moving the
  solve out of Python -- which is exactly what the batched GPU path does:
  one Python call performing B solves sidesteps the GIL by construction.

     A           439x639  nnz= 9759  density 3.48%
     reduced KKT 639x639  nnz=36661  density 8.98%

   exploits it.

2. fp64 ON THIS GPU IS 1/64 RATE. RTX 5070 Ti ~0.7 TFLOPS fp64, about par

  -> ~1.03x. PARITY, not acceleration.

CONCLUSION: at this problem size, on this hardware, batched dense GPU ADMM
does not accelerate the port. cuNRTO's 25.9x Franka result does not transfer
because their subproblem is ~10-100x larger and dense (K_v in R^2940,
thousands of SOC constraints); ours is n=639 at 0.16% Hessian density.

=== CAN A GPU OSQP HELP? (2026-08-21) — NO, LAUNCH FLOOR EXCEEDS DRAKE ===
Availability (scripts/gpu/osqp_backend_probe.py):
  osqp 1.1.1 -> algebras_available() = ['builtin'] only; algebra='cuda'
  raises "Algebra cuda not available". The published manylinux wheel ships
  only ext_builtin; osqp/cuda.py is a 4-line wrapper. cuosqp (the paper's
  package) has no installable distribution for this Python/CUDA.
  CUDA algebra = build OSQP from source with -DOSQP_ALGEBRA_BACKEND=cuda.
  Also: Drake vendors its own OSQP and always uses builtin, so a GPU OSQP
  would mean bypassing Drake entirely and feeding P/q/A/l/u ourselves.

Ceiling (scripts/gpu/gpu_osqp_ceiling.py, n=639 m=439 fp64):
  Drake CPU OSQP, in-run                47.5 us / iteration
  our batched GPU, batch=6              64.4 us   0.74x
  our batched GPU, batch=1             356.2 us   0.13x
  bare GPU kernel-launch floor          74.8 us   0.63x   <-- the hard limit

  The floor is only the kernel dispatches an OSQP iteration needs (2 matvecs
  + clamp + axpy), with no solver logic, preconditioner or termination check.
  It already costs 1.6x Drake's ENTIRE iteration. A GPU OSQP solves one
  problem at a time and so cannot amortise launches across samples; it sits
  at or above that floor by construction.

  Supersedes the earlier 41.8 us/sample-iteration figure (measured at m=300);
  at the real m=439 batched GPU is 64.4 us, a loss rather than a slight win.

=== CROSSOVER MAP: WHEN WOULD A GPU WIN? (2026-08-21) ===
scripts/gpu/crossover_sweep.py — us per ADMM iteration per sample, GPU
batch=6, fp64. Ratio > 1.00x means the GPU iteration is cheaper than Drake's.

              0.16%     5.00%    50.00%   100.00%   <- Hessian density
    n= 639     0.19x     4.47x     5.18x     8.52x
    n=1278     1.58x    34.12x    52.44x    32.80x
    n=2556    14.16x   125.14x   135.95x   137.50x

OUR PROBLEM IS THE TOP-LEFT CELL — the only losing cell in the entire plane.

Two crossings, both close by:
  density: at n=639, 0.16% -> 5% flips 0.19x -> 4.47x
  size   : at 0.16% density, n=639 -> n=1278 flips 0.19x -> 1.58x
So roughly a 2x horizon/contact growth, or any real Hessian coupling, and the
GPU becomes the right tool.

GPU time is nearly INDEPENDENT of density (n=2556 row: 159.58 / 158.14 /
159.56 / 158.91 us) and depends only on n. That is the launch/dense-work
signature: the GPU pays the same cost whether the matrix is 0.16% or 100%
full, because it does dense work regardless. The CPU meanwhile scales
steeply with both n and density (9.66 -> 21849 us across the plane).

CAVEAT — these synthetic instances are numerically EASIER than ours: the
synthetic CPU leg at our cell is 9.66 us/iter versus the 47.5 us/iter
measured in-run (real cond(K) ~ 1.2e7, real m=439 vs synthetic 304). So do
NOT read 0.19x as our margin. The authoritative figure for our problem is
the direct measurement: GPU 64.4 us vs Drake 47.5 us = 0.74x. The sweep's
value is the SHAPE of the crossover, not our own cell's absolute value.
Both agree on the sign: the GPU loses at our cell.
