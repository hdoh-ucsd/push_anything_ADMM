VERDICT: PROCEED, with design amendment A1.

  Why the isolated gate said STOP and the loop says PROCEED: a triangular
  solve is sequential back-substitution, the single most GPU-hostile kernel
  in the iteration. Everything else in the OSQP step (two batched matvecs,
  clamp, axpy) is embarrassingly parallel. Measuring the hostile op alone
  mispredicted the composite loop.

  A1 — replace cholesky_solve in the inner loop with cholesky_inverse
  (computed once per C3+ ADMM iteration, reusing the Cholesky factor) plus
  a batched GEMV. Same FLOPs, parallel instead of sequential, 4.41x over
  CPU. Legitimate because correction C2 already establishes that K changes
  only once per C3+ iteration while the RHS changes every inner iteration.

  Amortization is guaranteed: OSQP runs with check_termination=100, so the
  inner loop cannot stop before 100 iterations -- 10x the break-even.

  Use torch.cholesky_inverse(L), NOT torch.linalg.inv: 14.0 ms vs 31.0 ms.

OPEN RISK carried into Task 7: cond(K) = 5 was measured on RANDOM SPD
matrices. Real LCS instances may be worse conditioned. Task 7 must re-check
on the corpus, acceptance: explicit-inverse vs cholesky_solve relative
error < 1e-9 on every corpus instance. If any instance fails, fall back to
cholesky_solve for that (N, n_lambda) group and re-measure.

THE threads=4 RUN IS NOT A SPEEDUP -- THE PARALLEL PATH IS BROKEN.

  threads=1 : modes free=517 c3=284 ; goal_dist 0.150 -> 0.011 (min 0.0086)
  threads=4 : modes free=801 c3=0   ; goal_dist 0.150 -> 0.150 (NO progress)

  All 801 ticks in the threads=4 run read
      exec_src=current_fallback  pursued=kNewSample  best_other=-
  i.e. the controller asked for an alternative sample every tick and got
  nothing usable back, so it never repositioned, never entered c3, never
  touched the object. Final line: success=NO tight_goal=FAIL loose_goal=FAIL.
  It is "2x faster" only because it does no work.

  Also observed: curr_cost inflates from ~750 (threads=1) to ~1700 under
  threads=4, which points at state corruption in the shared-plant /
  per-worker-context dispatch (control/sampling_c3/inner_solve.py:1267-1291,
  `_run_one` calls self.plant.SetPositions on a shared plant object) rather
  than at the ranking logic. NOT root-caused further -- out of scope here.

=== Tasks 4/6/7 — corpus + GPU projection + GPU QP (2026-08-21) ===

Corpus (scripts/gpu/dump_admm_corpus.sh, 25 s box gate, seed 0):
  60 instances, each with inputs (.npz), CPU golden output (_out.npz) and the
  REAL assembled QP the CPU solved (_qp.npz). All (N=10, n_lambda=20),
  total_dim=639, admm_iter=3 -- the box task has a structurally fixed
  5-contact set, so batching needs no shape grouping here. Capture runs
  themselves reached tight_goal=PASS(final).

control/gpu/projection.py (Task 6): 16 tests, EXACT equality vs the numpy
  _project_C3Plus across 4 (u_lambda, u_eta) weight pairs, a dense boundary
  grid, batch independence, and the shipped project_C3Plus_eq12 helper.

control/gpu/batched_qp.py (Task 7): 7 tests.
  - matches OSQP on synthetic QPs to < 1e-4
  - no batch coupling; neighbours do not affect an element's answer
  - warm start reaches the same optimum
  - equality rows satisfied to < 1e-5

  Batch-vs-singleton is a TOLERANCE test (1e-10), not bit-equality, and
  deliberately: torch.linalg.cholesky is not bit-identical across batch
  sizes (cuSOLVER kernel selection; 3.5e-15 on K, 8.7e-18 on K^-1),
  compounding to ~6e-14 over 3000 iterations. A bare torch.bmm IS
  bit-identical across batch sizes, so this is the factorization kernel,
  not problem coupling.

AMENDMENT A1 OPEN RISK -- NOW CLOSED, and checking mattered:
  worst relative error over all 60 REAL instances : 9.348e-16
  worst cond(K) over all 60 REAL instances        : 1.229e+07

  Real instances are SIX ORDERS more ill-conditioned than the random SPD
  matrices (cond ~5) that originally justified A1. The explicit inverse
  nonetheless holds to 9.3e-16, far inside the 1e-9 acceptance bar, so A1
  stands. Had this been assumed rather than measured the design would have
  rested on an unrepresentative proxy.

End-to-end on a REAL assembled instance (n=639, m=439):
  GPU BatchedBoxQP vs tightly-converged OSQP: max|dx| = 8.803e-05.
  Note this is ~1e-4, not ~1e-9: the instances are ill-conditioned, so that
  is the achievable agreement scale. It is comfortably inside the plan's
  5e-3 acceptance bar on u_seq, and production OSQP itself runs at
  eps_abs = eps_rel = 1e-5.
