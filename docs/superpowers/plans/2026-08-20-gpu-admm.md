# GPU-Accelerated ADMM (C3+) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the C3+ ADMM inner loop (85% of wall time, per `memory/project_admm_perf_psd_check_2026-08-20.md`) onto the RTX 5070 Ti as a *batched, on-device* solver — batching over the per-tick samples and keeping all iterates on the GPU across ADMM iterations — behind an opt-in `PORT_GPU_ADMM=1` gate that is byte-identical OFF.

**Architecture:** One paper drives the design (accepted 2026-08-20; cuOSQP/arXiv:1912.04263 was considered and dropped by user decision — its regime is single huge QPs, n ≥ 10⁴, not ours):

**Wang/Abdul/Theodorou 2026 (arXiv:2603.02642, cuNRTO)** — the decisive lesson for *our* problem size: single QPs here are small (total_dim ≈ 500–900 for n_x=19, n_u=3, N=10, n_λ=6·n_c), so per-QP GPU parallelism alone wins nothing. cuNRTO's wins (up to 139×) come from (i) running the **entire inner ADMM loop on-device** with zero CPU↔GPU transfer inside the loop, (ii) **batching independent blocks** (their per-constraint SOC projections ↔ our per-sample solves), (iii) **factor-once, reuse triangular solves** across all inner iterations (their K_KKT Cholesky reused across DR/ADMM iterations), (iv) precomputed operator chains uploaded once per outer (CPU) iteration.

For the inner QP step we implement the standard OSQP ADMM iteration (Stellato et al., the algorithm Drake's `OsqpSolver` runs today) as batched dense torch ops — a fixed KKT system prefactored once per control step (cuNRTO's factor-once principle) plus an elementwise box projection `Π[l,u](z) = min(max(z,l),u)`.

Port mapping: outer loop = our control tick (Drake LCS linearization stays on CPU, exactly cuNRTO's host-side successive linearization); inner loop = outer C3+ ADMM × inner OSQP-style QP ADMM, fully on-device, **batched over the ~6 samples of the tick** (current + prev_repos + 4 strategy samples share shapes, differ only in data). Our projection is Bui eq. (12) componentwise (cheaper than SOC — closed-form per (λ,η) pair, elementwise on GPU).

**Tech Stack:** PyTorch ≥ 2.7 with CUDA 12.8 wheels (RTX 5070 Ti is Blackwell/sm_120 — older wheels won't run), float64 on device, `torch.linalg.cholesky` + `cholesky_solve` batched over samples. No custom CUDA kernels needed at these sizes. NumPy stays the interchange format at the module boundary.

**Non-negotiables (from standing rules):**
- This is a **perf** change in the same class as the 2026-08-20 PSD-check fix: solver semantics must be preserved, validated at the **solver level** with a replay corpus (sim-level hashes CANNOT validate — wall clock feeds the control law via `filtered_solve_time` → x-pred clamp).
- Default OFF. `PORT_GPU_ADMM` unset ⇒ byte-identical behavior (not one code path touched).
- Exact bit-identity with OSQP is **not** achievable (different inner QP algorithm/stopping); the acceptance bar is tolerance-based solver equivalence on a dumped-instance corpus + two-tier sim eval (60 s gate, 180 s canonical) with baseline at pre-change HEAD, per `feedback_two_tier_eval_protocol` and `feedback_baseline_provenance`.
- Commit before any long sim (WSL crash rule).

**Current hot-loop anatomy (verified against HEAD `018dffb`):**
- `control/admm_solver.py` `_solve_c3plus` (grep the symbol; ~line 1063): builds one Drake `MathematicalProgram` per control step — `AddLinearEqualityConstraint(C_eq, b_eq)` (x₀ pin + dynamics + η-definition rows), per-knot `AddBoundingBoxConstraint` on u slots / workspace state slots / EE-velocity slots, one `AddQuadraticCost(P_sym, 0)`. Then `admm_iter` times: `UpdateCoefficients(P_sym, q_total)` where only `q_total = q_ref − ρ·G·(δ−ω)` changes → `OsqpSolver().Solve(prog)` → closed-form `_project_componentwise(λ, η)` → ω-update. P_sym is constant across iterations (adaptive-ρ only fires every 10 iters; canonical admm_iter=3 never triggers it).
- `control/sampling_c3/inner_solve.py` `evaluate_samples`: sequential Python loop; each sample builds its own LCS (Drake, CPU — stays) then runs a `surrogate_admm_iters=3` solve. `resolve_at_full_iters` re-solves the winner.
- So per tick: ~6 samples × 3 ADMM iters × (1 OSQP setup+solve) ≈ 18–25 OSQP solves of a ~500–900-var QP, all sequential. This is the batch.

## Phase 1 — batched GPU QP solver (the inner-QP layer)

### Task 3: `BatchedBoxQP` — batched OSQP ADMM iteration in torch

Solves B independent QPs `min ½zᵀPz + qᵀz  s.t.  l ≤ Az ≤ u` sharing shapes. A stacks the equality rows (l=u=b_eq) and identity-selector rows for the box constraints — the exact constraint set `_solve_c3plus` gives Drake. Uses the **reduced KKT** system of the OSQP method (Stellato et al. §"solving the KKT system"): `(P + σI + AᵀRA) x̃ = σx − q + Aᵀ(Rz − y)`, prefactored with batched dense Cholesky and the factors reused across all iterations (cuNRTO factor-once principle); the reduced KKT matrix is PD for any σ>0, and at our sizes (≤ ~1000) batched dense Cholesky is the right tool — iterative/PCG methods pay off only for much larger n. ρ follows OSQP's convention: `10³·ρ̄` on equality rows, `ρ̄` on inequality rows.

```python
"""Batched dense OSQP ADMM iteration (Stellato et al.) in torch.

B independent box-constrained QPs sharing shapes:
    min ½ zᵀPz + qᵀz   s.t.  l ≤ A z ≤ u        (per batch element)
Reduced-KKT prefactored with batched Cholesky; every
iterate stays on-device (cuNRTO principle: no host transfer in the loop).
float64 throughout. ρ per-row per OSQP convention: equality rows get 1e3·ρ̄.
"""
from __future__ import annotations
import numpy as np
import torch


class BatchedBoxQP:
    def __init__(self, P, A, l, u, n_eq_rows: int,
                 sigma: float = 1e-6, rho_bar: float = 0.1,
                 alpha: float = 1.6, device: str = "cuda"):
        self.dev = torch.device(device)
        f64 = dict(dtype=torch.float64, device=self.dev)
        self.P = torch.as_tensor(P, **f64)            # (B, n, n)
        self.A = torch.as_tensor(A, **f64)            # (B, m, n)
        self.l = torch.as_tensor(l, **f64)            # (B, m)
        self.u = torch.as_tensor(u, **f64)
        B, m, n = self.A.shape
        self.alpha = alpha
        self.sigma = sigma
        rho = torch.full((m,), rho_bar, **f64)
        rho[:n_eq_rows] = 1e3 * rho_bar               # OSQP equality-row rho
        self.rho = rho                                 # (m,)
        self.rho_inv = 1.0 / rho
        K = (self.P
             + sigma * torch.eye(n, **f64)
             + self.A.mT @ (rho[:, None] * self.A))   # (B, n, n) PD
        self.L = torch.linalg.cholesky(K)             # factor ONCE

    def solve(self, q, max_iter: int = 1000, eps: float = 1e-6,
              z0=None, y0=None):
        f64 = dict(dtype=torch.float64, device=self.dev)
        q = torch.as_tensor(q, **f64)                 # (B, n)
        B, m, n = self.A.shape
        x = torch.zeros(B, n, **f64)
        z = torch.zeros(B, m, **f64) if z0 is None else torch.as_tensor(z0, **f64)
        y = torch.zeros(B, m, **f64) if y0 is None else torch.as_tensor(y0, **f64)
        for _ in range(max_iter):
            rhs = (self.sigma * x - q
                   + torch.einsum("bmn,bm->bn", self.A,
                                  self.rho * z - y))
            xt = torch.cholesky_solve(rhs.unsqueeze(-1), self.L).squeeze(-1)
            zt = torch.einsum("bmn,bn->bm", self.A, xt)
            x = self.alpha * xt + (1 - self.alpha) * x
            z_prev = z
            z_raw = (self.alpha * zt + (1 - self.alpha) * z_prev
                     + self.rho_inv * y)
            z = torch.clamp(z_raw, self.l, self.u)     # Π[l,u]
            y = y + self.rho * (self.alpha * zt + (1 - self.alpha) * z_prev - z)
            if _ % 25 == 24:                           # cheap periodic check
                r_prim = (torch.einsum("bmn,bn->bm", self.A, x) - z
                          ).abs().amax()
                r_dual = (torch.einsum("bnm,bm->bn", self.A.mT.mT.mT
                          if False else self.A.transpose(1, 2), y)
                          + torch.einsum("bnk,bk->bn", self.P, x) + q
                          ).abs().amax()
                if float(r_prim) < eps and float(r_dual) < eps:
                    break
        self._last = (x, z, y)
        return x.cpu().numpy()

    def solve_device(self, q_dev, max_iter=1000, eps=1e-6, z0=None, y0=None):
        """Same as solve() but takes/returns device tensors (Phase-2 path
        keeps the outer ADMM loop fully on-device)."""
        out = self.solve(q_dev, max_iter, eps, z0, y0)  # refactored in Task 5
        return torch.as_tensor(out, device=self.dev, dtype=torch.float64)
```

```python
import torch

def project_componentwise_batch(lam: torch.Tensor, eta: torch.Tensor):
    """Bui 2026 eq. (12) closed-form, elementwise over any shape.
    Transcribe the exact branch structure of
    C3Solver._project_componentwise (control/admm_solver.py) — the CPU
    function is the specification; this must match it to 1e-14.
    Sketch (verify against HEAD before trusting):
      case 1 (λ wins):  δ_λ = max(λ,0), δ_η = 0   if that point is nearer
      case 2 (η wins):  δ_λ = 0, δ_η = max(η,0)
      case 3: both already ≥0 with λ·η ≤ 0 handled per CPU code."""
    lam_p, eta_p = torch.clamp(lam, min=0.0), torch.clamp(eta, min=0.0)
    d_keep_lam = (lam - lam_p) ** 2 + eta ** 2          # project η→0
    d_keep_eta = lam ** 2 + (eta - eta_p) ** 2          # project λ→0
    keep_lam = d_keep_lam <= d_keep_eta
    d_lam = torch.where(keep_lam, lam_p, torch.zeros_like(lam))
    d_eta = torch.where(keep_lam, torch.zeros_like(eta), eta_p)
    return d_lam, d_eta
```

## Deferred / explicitly out of scope (YAGNI)

- **Custom CUDA kernels / cuDSS / PCG** — the papers' tools for n ≥ 10⁴ or thousands of cones; our QPs are ≤ ~1000 vars × ≤ ~10 batch. Batched dense Cholesky + elementwise ops cover it. Revisit only if Task 9 profiling shows the linear solve (not launch overhead) dominating.
- **float32** — free 2× on paper, but the conformance mission makes precision drift a liability. Not until float64 lands and holds.
- **GPU-side LCS linearization** — Drake autodiff stays on CPU (cuNRTO keeps successive linearization on host too); it's ~15% of wall time, Amdahl-capped.
- **Adaptive-ρ ≥10-iter path, §7.67 B1-A, Lorentz C3 (`mode='c3'`)** — CPU fallback; `mode='c3'` is a falsification lever only.
- **jack task** — validate on box + T first; jack adds per-task scales but no new solver structure.
